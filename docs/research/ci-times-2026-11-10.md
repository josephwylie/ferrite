# CI times: why Windows takes 25 minutes — 2026-11-10

Follows [rust-compile-benchmark-2026-11-09.md](rust-compile-benchmark-2026-11-09.md), which looked at rustc frontend threads on a workstation and found nothing worth changing. This note covers CI only. The workflow is `.github/workflows/ci.yml` as of 5c6fae3d (#209).

**[M]** means measured from this repo's runs (run IDs given). **[E]** means estimated. **[D]** means a primary-source fact (official docs or source). **[C]** means a community claim, listed separately at the end.

## Short answer

The Windows job is slow because it **starts with an empty Rust cache on every run**. The same job finished in **11m02s** when its cache was warm, against **25m41s** cold [M: 40289698335 on 2026-10-26, 42754659261 for #209]. The cache is empty because no main run has saved a Windows Rust cache since 2026-10-27, for three reasons:

1. Main runs get cancelled. `cancel-in-progress: true` applies to pushes to main as well as PRs. The cancelled job skips rust-cache's save step [M: 42757048510, where Windows `Post Run Swatinem/rust-cache` was *skipped*]. rust-cache saves only on `success()` unless `cache-on-failure` is set [D: action.yml `post-if`].
2. Main was red. Every main run between 2026-10-27 and 2026-11-10 failed or was cancelled on Windows [M: `gh run list --branch main`]. rust-cache does not save on failure by default [D: README `cache-on-failure`].
3. Unused caches are evicted after 7 days, and PR caches use most of the 10 GB. GitHub deletes cache entries not accessed in over 7 days and evicts the least recently used once the repository exceeds 10 GB [D: GitHub caching docs]. The repository was at **10.46 GB, 3,360 entries** [M: `gh cache list`]. About 6 GB of that sat in PR scopes (`refs/pull/N/merge`) that no other PR can restore. Each PR saves its own ~0.9-1.0 GB rust-cache entry per OS. The last Windows main save (2026-10-27) is gone.

macOS does not have this problem: its job passed on main, so it restores an ~880 MB main-scoped rust-cache and finishes in ~5 min [M: 42754659261].

Where the 25m41s Windows time goes in #209's run (cold rust-cache, sccache 88% hits, CEF cache miss) [M: 42754659261]:

| Step | Time | Of which |
|---|---|---|
| Build app with visuals | 15m27s | ~7.6 min dependency graph (GPUI stack, `windows*`); ~5.5 min `cef-dll-sys` build script (CEF download plus CMake/Ninja build of `libcef_dll_wrapper`), during which nothing else compiles; ~2.3 min `ferrite-pane` → `ferrite` compile and link |
| Test core | 6m56s | 4m21s compile (≈3 min of it dependencies; ≤52 s for `ferrite-core` itself plus all 48 test executables); 2m34s running tests, of which the lib unit-test binary takes 127 s (macOS: 54 s) |
| Review core tests | 1m43s | 26 s compile, ~77 s run |
| rust-cache save | 53s | 925 MB upload |
| Setup | ~27s | |

Ranked: (1) the cold Rust cache, which turns ~1 min of dependency work into ~10 min; (2) the serial CEF wrapper build and download on a cold target; (3) Windows test execution, about 2.3× slower than macOS; (4) linking and integration-test count, both small.

In the warm 2026-10-26 run, the same steps took: Test core 5m42s (1m28s compile, then a 187 s lib test run), Review 1m20s, Build app 1m22s, Visuals 59s with a CEF cache hit [M: 40289698335].

## Recommendations

### 1. Let main save the Windows cache, and stop PRs filling the 10 GB — saves ~14 min per Windows run [M baseline, E saving]

- **Don't cancel main runs.** Use `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`. The docs allow an expression here using the `github` context [D: workflow syntax, concurrency]. Without this change, merging two PRs within ~25 min means main never saves a Windows cache.
- **Add `cache-on-failure: true` to rust-cache**, so a red main or a failed test still saves the compiled dependencies [D: rust-cache README]. The CEF cache already does the equivalent since #209.
- **Save rust-cache only from main:** `save-if: ${{ github.ref == 'refs/heads/main' }}`. The README gives this exact pattern [D]. GitHub scopes PR caches to the merge ref, so other PRs can never restore them [D: GitHub caching docs]. Today each PR adds ~1.9 GB of rust-cache entries plus ~0.36 GB of CEF, which evicts main's caches under the 10 GB LRU limit [M: `gh cache list`]. A PR still restores main's cache [D].
- Expected effect: Windows goes from ~25-30 min to ~11-13 min, using the measured 11m02s warm run as the baseline. The code has grown since 2026-10-26, so treat the target as [E]. The "Build app" step it included has since been removed, so the warm total should be lower again.
- Cost/risk: one YAML change. Main runs now queue instead of cancelling, which uses more runner minutes; standard runners are free for public repos [D: runners docs]. If a PR changes `Cargo.lock`, it restores main's cache through rust-cache's prefix restore key and rebuilds only what changed [M: both OS keys share a restore key like `v0-rust-windows-Windows_NT-x64-35d44785`].
- The main run for #209 (42758326358) was still running when this note was written. If its Windows job succeeds, it will seed a main Windows cache once. The next cancelled or failed main run, and then the 7-day rule, undo that.

### 2. Run the Windows visuals build as a separate job, in parallel with the tests — cold: ~8 min wall; warm: ~1 min [E]

On Windows, the tests and the visuals build share almost nothing. In #208, `--features cef` after a plain `cargo build -p ferrite` still recompiled 104 crates, including `gpui-pre`, `windows-sys`, `ferrite-core` and `ferrite-reviewr`, and took 12m36s [M: 42747789209]. The likely cause is Cargo's feature unification: new features enabled on shared dependencies change their build hash. Cargo builds a shared dependency with the union of features it needs and warns that this can mean building the same dependency more than once [D: Cargo features]. This is not confirmed with `cargo tree -e features`. Two jobs would each run the critical path on their own: about 8.6 min (tests) next to about 15.5 min (visuals) when cold.

- Cost/risk: a second Windows runner per run, about 30 s of extra setup, and a second rust-cache key (the key already includes the job ID [M: `add-job-id-key: true`]). With recommendation 1 in place, the warm visuals build is ~1 min [M], so this mainly helps when the cache is cold. **Do recommendation 1 first. Do this only if cold runs stay common**, for example after dependency bumps.

### 3. Find out why Windows tests run 2.3× slower than macOS — up to ~1.5 min [E]

The `ferrite-core` lib unit-test binary (1,052 tests) took 127 s on Windows against 54 s on macOS [M: 42754659261], and 187 s in the 2026-10-26 run [M]. The Windows runner has more cores (4 vCPU, 16 GB) than macOS (3 M1 cores, 7 GB) [D: runners docs]. CPU therefore doesn't explain the gap; slow process creation or file I/O on Windows is the likely cause. Next step: get per-test timings (for example by running that binary under cargo-nextest once) to find long-pole tests. Also try the Dev Drive / Defender reports below. Cargo runs test binaries one after another [D: Cargo targets]. Nextest runs every test in its own process, in parallel [D: nextest "how it works"]. That gives some overlap, but on Windows the per-process cost may cancel it out [E]. Measure before adopting.

### 4. Smaller, cheap or optional

- **Consolidate `ferrite-core` integration tests [E: ≤ ~40 s on Windows].** There are 48 test executables on Windows, and 32 of them run zero tests there (cfg'd out) but are still compiled and linked [M: 42754659261]. Cargo builds each `tests/*.rs` as its own crate and executable, and suggests one integration test crate with modules when there are many [D: Cargo targets]. On Windows, everything after `ferrite-core` started compiling took only 52 s in total [M], so the gain is capped. Do it for tidiness, not for speed.
- **rust-lld on Windows [E: < 1 min].** rust-lld is the default linker only on `x86_64-unknown-linux-gnu` (since 1.90) [D: Rust blog 2025-09-01; rustc codegen options]. MSVC targets still use `link.exe`, and the `lld-link` flavor is an opt-in [D: rustc codegen options]. Linking is a small share of the measured time here: test binaries ≤52 s including compiling, and the final app is inside a 2.3 min tail. Lower priority than 1-3. CEF/GPUI compatibility with lld-link is unverified.
- **macOS: drop either the plain or the cef "Build app" step [M: ~30-40 s].** When warm, each takes ~30 s [M: 42754659261]. The plain build is the only check that a build without the `cef` feature compiles, so keeping it is a judgement call.
- **Larger runners: not available.** They require an organization on GitHub Team or Enterprise Cloud [D: runners docs]. This repository belongs to a personal account. It is public, so it already gets the 4 vCPU / 16 GB standard Windows runner rather than the 2 vCPU one private repos get [D].

### Already right, or not worth changing

- `CARGO_INCREMENTAL=0` is required for sccache to cache workspace crates: sccache cannot cache incremental compilations [D: sccache README]. `debug = 0` turns debug info off completely [D: Cargo profiles]. Keep both.
- **sccache misses are mostly by design.** In #209's Windows job there were 206 non-cacheable calls: 90 `bin`, 47 `proc-macro`, 51 other crate types [M]. sccache cannot cache crates that invoke the linker (`bin`, `dylib`, `cdylib`, `proc-macro`) [D: sccache README]. The 83 real misses averaged 15 s of compile each; a hit took 0.26 s to read [M]. Hits require matching absolute paths [D]. The workspace path (`D:\a\ferrite\ferrite`) is stable across runs, so `SCCACHE_BASEDIRS` is not needed.
- The sccache GHA backend stores many small entries: 2,163 entries, 1.9 GB on main [M]. If it hits the service rate limit, the build continues and the write may be skipped [D: sccache GHA docs]. No rate-limit errors appeared in these runs [M: `Cache write errors 0`].
- `[profile.dev.package."*"] opt-level = 2` makes cold dependency builds slower but, per the Cargo.toml comment, halves test run time. Build scripts and proc-macros stay at opt-level 0 by default [D: Cargo profiles]. With a warm cache the dependency cost is paid once. Keep it.
- `split-debuginfo` and `codegen-units`: debug info is off, so split-debuginfo does nothing here. Non-incremental builds already default to 16 codegen units [D: Cargo profiles]. No change.

## Community reports [C]

These are other people's results, not checked against this repo. Each has its link and date.

**Windows disk and antivirus (supports recommendation 3)**
- astral-sh/uv PR #3522, "speed up windows jobs using ReFS" (merged 2024-05-13): https://github.com/astral-sh/uv/pull/3522. Moving Windows CI work onto a ReFS volume cut cargo tests from 8 min to 4-5 min and a binary build from 4 min to 1-2 min; the author sums it up as "1.5x-2x". This is the strongest measured Windows result found.
  - Our job already checks out to `D:\a\ferrite\ferrite`. `CARGO_HOME`, `TEMP` and the CEF directory stay on `C:` [M: log paths].
  - Moving those, or the whole build, onto a Dev Drive is the experiment this suggests. [E: perhaps 1-3 min; unmeasured here.]
- samypr100/setup-dev-drive: https://github.com/samypr100/setup-dev-drive. It claims "about 25% or more" faster builds and tests, with no methodology given.
- Richard Si, "Faster pip CI on Windows" (2025-03-10): http://sichard.ca/blog/2025/03/faster-pip-ci-on-windows-d-drive/. Pointing `TEMP` at `D:` cut his jobs by 10-28%; ReFS on top saved about 1 more minute. He guesses Defender is already off on GitHub runners but did not verify it, and the workload is Python.
  - GitHub's runner docs found here say nothing about Defender. This is **unverified**.
- Dioxus `.github/workflows/setup-dev-drive.ps1`: https://github.com/DioxusLabs/dioxus/blob/main/.github/workflows/setup-dev-drive.ps1. It creates a Dev Drive with antivirus disallowed, because scanning `.o`, `.rlib` and `.exe` files is "extremely expensive". No numbers.

**Linker (agrees with recommendation 4)**
- rust-lang/rust #71520, "Use lld by default on x64 msvc windows": https://github.com/rust-lang/rust/issues/71520. Still open as of 2026-11-06.
  - A 2026-11-06 comment measured ripgrep's incremental rebuild with rustc 1.96: 1,714 ms down to 1,503 ms in total, and the link phase 1,020 ms down to 712 ms.
  - Gains of about 0.3 s per link agree with the primary docs that lld is not the MSVC default, and with our measurement that linking is a small share of the time.
- Rust blog, 2025-09-01 (linked above): about 7x faster linking on Linux for ripgrep. It covers Linux only.

**sccache with the GitHub Actions cache backend (refines "already right")**
- mozilla/sccache #1485, "GitHub Actions cache is surprisingly slow" (opened 2022-12-18): https://github.com/mozilla/sccache/issues/1485. The cache service answered with HTTP 429 errors and `Retry-After` waits of up to 60 s, turning a ~10 min job into ~1 h.
- GitHub changelog, 2026-01-16 (primary source): https://github.blog/changelog/2026-01-16-rate-limiting-for-actions-cache-entries/. Uploads of new cache entries are limited to **200 per minute per repo**, because bursts of uploads "increase cache thrash".
  - Our Windows job wrote 83 entries in about 25 min [M], so we are well under the limit.
  - Still, sccache's 2,163 small main entries share the same 10 GB quota as rust-cache [M].
- wez/wezterm PR #4468 (merged 2024-02-01): https://github.com/wez/wezterm/pull/4468. After switching to sccache, a Windows job with a warm cache got 0 hits and 702 misses. That conflicts with our measured 88% Windows hit rate, so their failure was probably specific to their setup.
- Zed (zed-industries/zed, workflows read 2026-11-10): https://github.com/zed-industries/zed/tree/main/.github/workflows. Zed runs Windows on self-hosted 32-vCPU machines and uses sccache backed by Cloudflare R2, not the GitHub cache. It sets `CARGO_INCREMENTAL=0` and uses no custom linker on Windows.

**Caches saved only from the default branch (agrees with recommendation 1)**
- Tauri `.github/workflows/test-core.yml`: https://github.com/tauri-apps/tauri/blob/dev/.github/workflows/test-core.yml. It uses rust-cache with `save-if: github.ref == 'refs/heads/dev'`, explaining that PR saves cannot be restored elsewhere and evict default-branch caches. This is the same reasoning as recommendation 1.
- Bevy: https://github.com/bevyengine/bevy/tree/main/.github/workflows. CI only restores caches; a scheduled `update-caches.yml` workflow saves them. CI sets `CARGO_INCREMENTAL=0` and `CARGO_PROFILE_{DEV,TEST}_DEBUG=0`, as we do.
- rust-analyzer runs Windows CI with no Rust cache at all and uses nextest: https://github.com/rust-lang/rust-analyzer/tree/master/.github/workflows

**Test layout and runner**
- matklad, "Delete Cargo Integration Tests" (2021-02-27): https://matklad.github.io/2021/02/27/delete-cargo-integration-tests.html. One integration-test binary made Cargo's own test compile about 3x faster and its artifacts about 5x smaller.
  - Our measured ceiling for this is low: ≤52 s for all of `ferrite-core` plus its tests [M]. Expect far less than 3x here.
- nextest benchmarks (page dated 2022-02-11, updated 2026-07-09): https://nexte.st/docs/benchmarks/. Test runs are 1.37x-3.38x faster than `cargo test` on a 16-core 7950X, build time excluded.
- corrode.dev, "Tips for Faster Rust CI Builds" (Matthias Endler, 2025-01-28, updated 2025-08-16): https://corrode.dev/blog/tips-for-faster-ci-builds/. He sees about 40% from nextest in CI rather than 3x, because CI runners have fewer cores. He also recommends `CARGO_INCREMENTAL=0` and test debug info off, both of which we already do.

No measured Windows CI reports were found on r/rust or users.rust-lang.org.
