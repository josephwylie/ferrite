# Remote connection parity acceptance

This matrix describes the proof required for PR 310 to match the actual T3 remote workflow. It records intended coverage, not a passing result. The parent reviewer owns the visual verdict after opening both original captures and their comparisons.

The new verifier is `scripts/verify-remote-parity.py`. It imports process and SSH helpers from the previous verifier without changing those helpers or replacing earlier evidence. Every run needs a new output directory. Its `summary.json` distinguishes functional assertions, visual review, actual model verification, and cleanup.

## Run the final native verification

Build and integrate the worker changes before running this command. The user waits on each test run, so run the complete native flow once after the final edits.

```sh
python3 scripts/verify-remote-parity.py \
  --output /absolute/path/to/new-evidence-directory \
  --binary /absolute/path/to/ferrite \
  --server /absolute/path/to/ferrited \
  --size 1440x900 verify
```

Use the same logical viewport as the actual T3 capture. The verifier starts a nonroot task-owned OpenSSH server, separate client and remote Stores, the actual Ferrite Server, the native headless window, and the actual remote gateway. It uses preinstalled task-owned binaries. It does not test a published cold installer.

`window attach /absolute/path/to/screenshot.png` stages files through the same `Composer::add_local_files` call as the native picker. The normal edited subscription starts the upload. This action does not fabricate attachment readiness or a remote file. It does not exercise the operating system's file picker.

The verifier installs a Codex app-server fixture on its isolated PATH and a Claude launcher that refuses all model operations. It does not make model API calls. A separate actual Codex smoke, if run by the parent, must be recorded as separate evidence.

If verification fails, preserve its output and failure screenshot. A repeat run needs a different directory. `stop` rechecks the recorded process identities and stops only that run's surviving processes.

## Compare actual captures without resizing

Each native PNG has a JSON sidecar containing its SHA-256, actual PNG dimensions, logical viewport, device pixel ratio, source commit, binary hash, and crop rectangle. Add equivalent sidecars for the actual T3 screenshots. Record the installed T3 version and capture method in those sidecars. Keep the original screenshots unchanged.

A sidecar has this structure. Values below illustrate the format and are not capture evidence.

```json
{
  "path": "actual-t3-remote-modal.png",
  "sha256": "sha256-of-the-original-file",
  "logical_viewport": [1440, 900],
  "device_pixel_ratio": 2,
  "png_dimensions": [2880, 1800],
  "crop_px": [0, 0, 2880, 1800],
  "surface": "Actual installed T3 native application",
  "installed_version": "record the observed version",
  "capture_method": "record the actual capture method"
}
```

A comparison manifest names sidecars relative to itself.

```json
[
  {
    "name": "add-remote",
    "t3": "t3/remote-modal.json",
    "ferrite": "native/02-add-remote-default-1440x900.json"
  }
]
```

Run the compositor after both sets of screenshots exist. It requires Pillow. It verifies source hashes and PNG dimensions, then rejects unequal logical viewports, device pixel ratios, or crop dimensions. It places the native pixel crops side by side and labels their dimensions. It does not scale or retouch either source.

```sh
python3 scripts/verify-remote-parity.py compose /absolute/path/to/comparisons.json
```

The compositor writes a comparison PNG and provenance JSON. Its verdict remains `requires parent visual review`. Functional assertions do not establish matching appearance. Differences in the installed T3 version, fixture content, and desktop chrome must remain explicit in the final verdict.

## Narrow verification commands

The verifier and controller changes have these scoped checks. The parent runs the Rust checks after integrating the attachment handler and counts the results once.

```sh
python3 -m py_compile scripts/verify-remote-parity.py
cargo nextest run -p ferrite-core --lib -E 'test(api::tests::) | test(server::tests::drive::)'
cargo check -p ferrite --features headless
```

The native flow is the E2E check for this change. The Python syntax check alone does not establish runtime correctness.
